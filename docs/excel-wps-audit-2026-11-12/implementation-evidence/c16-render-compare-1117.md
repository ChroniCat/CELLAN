# C16 逐页渲染比对（首次真渲染，不是只查 PDF 头）

原台账写着「没有逐页 Excel/WPS 视觉矩阵」。这次补上了可复现的比对工具，
并把**测量到的差距**如实记下来——所以 C16.2/C16.3 **仍不判验收**。

## 方法

1. Excel 自己导出 `ExportAsFixedFormat(0, …)`：`scripts/c16_excel_pdf.ps1`
   → `work/probe/c16/{print,objects}-excel.pdf`
2. 本引擎导出：`cargo run -p sheetcore --example c16_pdf -- …`
   → `{print,objects}-ours.pdf`
3. python 侧（`uv run --with pypdfium2 --with pillow --with numpy`）：
   - `scripts/c16_pdf_compare.py`：页数、页面尺寸、墨量比、灰度 MAE、逐页文本串
   - `scripts/c16_pdf_pos.py`：指定 token 的字符框坐标（pt）

## print.xlsx（2 页，重复标题行 + 合并标题 + 换行 + 负数红字）

```text
pages ours=2 excel=2
p1 595x842 / 595x842  ink 0.059 vs 0.043  mae 10.8   text 794 vs 794 chars
p2 595x842 / 595x842  ink 0.028 vs 0.023  mae 3.8    text 250 vs 250 chars
```

token 坐标（pt，`d=(dx,dy)`）：

```text
页1 '2026 年第一季度销售汇总' ours=(128.3,750.3) excel=(116.7,749.8) d=(11.6,0.5)
     '产品'                  ours=(97.4,724.4)  excel=(93.9,722.5)  d=(3.5,1.9)
     '铅笔'                  ours=(56.3,713.6)  excel=(56.8,705.1)  d=(0.5,8.5)
     '¥1,234,567.89'         ours=(399.6,640.3) excel=(373.1,631.8) d=(26.5,8.5)
     '--987.65'              ours=(430.1,663.2) excel=(400.8,655.5) d=(29.3,7.7)
页2 标题/表头同上（重复标题行生效），数据行只在各自页出现
```

结论：**内容无漏项（每页字符数相同）、页数/页面尺寸一致**；但**位置有系统偏差**：
横向 0~31pt（字形宽度估算 vs Excel 真字体度量）、纵向 0~8.5pt（行高/基线模型）。
这正是 C16.2 不能判验收的原因，且现在有了可量化的回归基线。

### 列几何：与 Excel 完全一致

A=108 B=60 C=60 D=84 E=18 F=96   A:D=312

### 剩余偏差归因（不是列宽问题）

- 横向：右对齐数字的起点差 26.5pt（`¥1,234,567.89`）。列右边界一致，因此差异来自
  **字形宽度**：Excel 用 Calibri，我们渲染用 Noto Sans SC，且排版宽度用 0.55×字号估算。
  试过挂真 Noto 度量，偏差反而从 26.5pt 变 35.0pt（Noto 比 Calibri 窄），故回退——
  要真正对齐需度量兼容字体（Carlito 一类），这是字体资产问题，不是排版代码问题。
- 纵向：数据行整体比 Excel 高 8.5pt，标题行只差 0.5pt；行距实测 13.5 vs 13.56pt。
  差异来自标题块/表头块的高度累计（`print.paginate` 的 head 高度计算），待单独校正。

C16.2/C16.3 仍为待验收；上述两条是有刻度的下一步（横向等字体资产、纵向改 head 累计）。

## 更正（同日，必须撤回上一条里的“纵向 8.5pt 行高问题”）

上一条把「数据行整体高 8.5pt」写成行高/表头累计问题，**这个归因是错的**，撤回：

- 两页的行数其实完全相同：第 1 页都到「行48」，第 2 页都是「行49–60」。
  之前看到“我们多一行”是截断输出造成的误读。
- 行距实测：Excel 40.68pt / 3 行 = 13.56，我们 40.5 / 3 = 13.50，差 0.06pt/行。
- 那 8.5pt 是**字形包围盒差异**：`charbox` 给的是字形外框底，不是基线；
  Noto 的 CJK 外框比 Excel 用的字体低 8pt 左右，整串一起平移，看起来像“行高不同”。

同样要更正横向那条的归因：不是“字形宽度导致左移”，因为
`¥1,234,567.89` 的**左右边缘同时右移 25pt**（Excel 373.1–443.9，我们 399.6–469.0），
整串平移而非变宽。列宽已用 COM 证实逐列相同（108/60/60/84/18/96），
所以剩下的是 F 列文本的水平定位问题，需要单独 dump 坐标，不再凭一次对比下结论。

## 现在能确定的 C16 差异（都可复跑）

1. A8 自动换行的断行位置不同（Excel 断在「…折/行」，我们断在「…不/能」）——排版宽度估算所致。
2. F 列右对齐文本整体右移约 25pt（列宽相同，定位不同，待查）。
3. 同一页内文本绘制顺序不同（Excel 把合并标题画在最后，我们按行从上到下）——只影响文本提取顺序，不影响视觉。
4. 数值轴刻度已修好（0/5/10/15/20/25 完全一致）。
