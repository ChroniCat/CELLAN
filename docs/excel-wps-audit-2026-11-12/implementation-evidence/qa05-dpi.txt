QA-05.2 100/125/150/200 DPI 基线（含真崩溃修复）
================================================================================
日期：2026-11-16

一、方法
--------
新增 `SC_PPP`（启动时 `ctx.set_pixels_per_point`），逻辑尺寸固定 1280×800 点，
物理像素 = 1280×ppp，等价于同一界面在高 DPI 屏上：物理尺寸不变、像素更密。

探针：`work/probe/qa05/run_dpi_probe.ps1`（设 SC_PPP / SC_WIN_W / SC_WIN_H / SC_SHOT，
跑完自动退出并落 PNG）。截图走应用自身 framebuffer（本机 RDP 下 GDI 截图失效，这条路可用）。

二、结果
--------
| ppp | 物理分辨率 | 截图 | 命名按钮数 | 粘贴按钮物理尺寸 |
|---|---|---|---|---|
| 1.00 | 1280×800 | dpi5-1.0.png | 40 | 42×76 |
| 1.25 | 1600×1000 | dpi5-1.25.png | 33 | 52×95 |
| 1.50 | 1920×1200 | dpi5-1.5.png | 29 | 63×114 |
| 2.00 | 2560×1600 | dpi5-2.0.png | 21 | 84×152 |

- **物理尺寸按 ppp 精确缩放**：42×76 → 52×95（×1.25）→ 63×114（×1.5）→ 84×152（×2.0），
  没有出现「高 DPI 下按钮变小/变大」的漂移。
- 降采样到 720×450 后与 1.0 对比：1.25 平均差 3.17（2.70% 像素显著差）、
  1.5 平均差 3.21（2.30%）——差异集中在文字抗锯齿，布局一致。
- 逻辑宽度 1280→1024→853→640 时按钮数 40→33→29→21，是功能区按宽度收组的
  自适应行为（UI-13），不是裁切。

三、抓到的真崩溃（已修）
------------------------
`960×600` 逻辑尺寸 + ppp 1.5 启动直接 panic：
```
thread 'main' panicked at core/src/num/f32.rs:1605:
min > max, or either was NaN. min = 24.0, max = 17.0
  app::zoom_bar
```
定位到滚动条拇指长度：
```rust
let thumb_len = (span * frac).clamp(24.0, span);   // span=17 时 min>max
```
窄窗口/高缩放下滚动条可用长度可能小于 24px，`clamp(24.0, span)` 直接违反 clamp 前提。
修为 `if span <= 24.0 { span } else { (span * frac).max(24.0).min(span) }`；
另外给 `zoom_bar` 加了退化矩形保护（`rect.width() < 24.0` 直接返回）。
修完 960×600@1.5 正常出图（`work/probe/qa05/bt.png`）。

顺带修：拆分按钮主体的可访问矩形把箭头区也算进去了（粘贴 42×76 与箭头 42×12 完全重叠），
现在主体矩形止于箭头顶部（42×64 + 42×12 相邻不重叠）。

四、边界（口径）
----------------
- `SC_PPP` 走 egui 的 `set_pixels_per_point`，与 eframe 接收系统 DPI 后用的是同一机制；
  但**没有在真实 125/150/200% 系统缩放设置或第二块显示器之间切换过**（RDP 会话做不到）。
- 视觉相似度用像素差指标 + 尺寸核对，**没有做人工视觉基线评审**：
  本轮 `vision_analyze` 连续超时（图片服务不可用），所以不作「肉眼一致」的结论。
- 没有覆盖 760×420 最小窗口之外更极端的尺寸；工具栏溢出菜单也未验证。
