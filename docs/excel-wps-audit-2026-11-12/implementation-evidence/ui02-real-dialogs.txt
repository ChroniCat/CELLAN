UI-02 复核补正：Ctrl+Shift+S / Ctrl+O 真的弹出系统对话框
=======================================================
日期：2026-11-12 UTC+08

一、复核指出的问题
------------------
原来的 `ctrl_shift_s_saves_to_a_new_path_and_keeps_the_original` 等用例，通过 `SC_SAVE_AS` /
`SC_OPEN_PATH` 直接把路径塞给保存/打开逻辑，**绕过了系统对话框**。
按键事件注入本身是允许的（要求原文就是「测试必须注入按键事件或驱动真实窗口」），
但「按了键之后弹不弹系统另存为」这件事，绕过对话框的测试证明不了。

二、改动（保留原有事件回归，不删任何测试）
------------------------------------------
新增两个 GUI 用例，真的启动 app.exe、真的触发命令、从**外部**用 Win32 API 检查窗口：

1. `save_as_command_shows_a_real_system_dialog_and_cancel_keeps_the_file`
   - 合成 `ui_saveas.xlsx`，记录 SHA256 与运行目录里 xlsx 数量；
   - 起 app，`SC_RIBBON_ACTION=FileSaveAs`（与功能区「另存为」同一个 `onAction`，
     最终走 `command_exec("FileSaveAs")` → `save(true)` → `rfd::FileDialog::save_file()`）；
   - `EnumWindows` 遍历该 PID 的可见顶层窗口，按类名/标题找对话框；
   - 找到后向它 `PostMessage(WM_CLOSE)`，等价于用户点「取消」；
   - 断言：对话框确实出现、原文件 SHA256 不变、运行目录里没多出 xlsx。
2. `open_command_shows_a_real_system_dialog`
   - 同样流程跑 `FileOpen`（Ctrl+O 的同一条命令），断言出现系统「打开」对话框、文件未被改动。

三、真实输出
------------
    test real_dialogs::save_as_command_shows_a_real_system_dialog_and_cancel_keeps_the_file ...
      另存为对话框：class=#32770 title=Save As
    ok
    test real_dialogs::open_command_shows_a_real_system_dialog ...
      打开对话框：class=#32770 title=Open
    ok
    test result: ok. 2 passed; 0 failed; finished in ~4.4s

`#32770` 是 Windows 通用对话框的窗口类，`Save As` / `Open` 是它的标题——
这不是 SC_* 钩子能伪造的东西：钩子只能给逻辑一个路径，给不出一个真实的系统窗口。

四、Ctrl+S 的「原文件完整哈希」
------------------------------
`ctrl_s_saves_the_open_file_after_a_typed_edit` 补充了文件级断言：
保存前记 `SHA256(file)`，Ctrl+S 之后必须**变化**（证明磁盘上真的被替换，而不是只清了内存 dirty），
再 `xlsx::load` 读回 A1 = 123。

五、仍然没做的
--------------
- 对话框**内部**的确认动作没自动化：没有在 Save As 里选目录、填文件名后点「保存」，
  也没有在 Open 里选中文件后点「打开」。现有证明是「对话框真的弹出」「取消后原文件不变」，
  以及事件层「给定路径后能正确保存/打开」（由 SC_SAVE_AS / SC_OPEN_PATH 用例覆盖）。
- 系统对话框的非模态行为（本项目 `rfd` 用的是阻塞式对话框，Excel 用的是窗口内模态）
  属已知差异，登记在案。
