C01.2 修正 + C01.3 FORMULA 缓存布局与真实局部增量
==================================================
日期：2026-11-13 UTC+08   对标：core-requirements.md C01（C01.2 补正、C01.3）

> 本文件有过一次返工：第一版 C01.3 的矩阵里放了成功的 `SEQUENCE` 溢出，
> 于是 `recalc_dirty` 每次都整本回退全算，多轮其实是「全量 vs 全量」；
> 溢出障碍还写错了列（占 B9 不挡 A9:A10 的单列溢出）。第五节如实记录，
> 第六节是返工后的真实局部路径验证。

一、复核指出的读取回归（已证实）
------------------------------
上一版 `xls_read` 用「两种布局都接受」的启发式：

    if body[6] == 0xFF && body[7] == 0xFF { (body[8], body[9]) }
    else if body[12] == 0xFF && body[13] == 0xFF { (body[6], body[8]) }

`body[6..8]` 是 num 字段的**低 16 位**，普通 finite double 完全可能是 0xFFFF：

    f64::from_bits(0x3ff000000000ffff) = 1.0000000000145517
    小端字节 = ff ff 00 00 00 00 f0 3f      ← body[6..8] 命中

于是这个合法数值被判成特殊值，`ty = body[8] = 0x00`（字符串）→ 不 push → **整格丢失**。

二、规范依据（不是猜的）
------------------------
calamine 0.38 `xls.rs::parse_formula_value`（`r` = `body[6..14]`）：

    [0x00, .., 0xFF, 0xFF] => 字符串（值在下一条 STRING 记录）
    [0x01, _, b, .., 0xFF, 0xFF] => Bool(b)
    [0x02, _, e, .., 0xFF, 0xFF] => 错误 e
    [0x03, .., 0xFF, 0xFF] => 空
    _ => 普通 f64

即：**高两字节 num[6..8] == 0xFFFF 才是特殊值**，num[0] = 类型，num[2] = 取值。
高两字节 0xFFFF 对应符号位 1 + 指数全 1，只能是 NaN，不可能是真数值 —— 这才是可判的边界。

三、改动
--------
1. `xls_read`：只按高两字节判特殊值（删掉低两字节分支），type=body[6]、val=body[8]。
2. `xls_read`：补 **STRING 记录**（0x0207）——之前完全没有这个分支，
   我们自己写出去的文本公式缓存读回来是空的。
3. `xls_write::cached_value`：标号从 `num[0..2]` 挪到 `num[6..8]`（type=num[0]、value=num[2]）。
   旧写法只有我们自己的旧读端能认，Excel 会把缓存读成 NaN。

五、第一版 C01.3 的名义覆盖（返工原因）
--------------------------------------
1. `book()` 里 A9=`=SEQUENCE(2,1)`、障碍放在 **B9**：单列 2 行溢出占 A9:A10，
   B9 根本不挡路 → 这是**成功的溢出**，不是 `#SPILL!`。
2. 因为簿子里有 `spilled`，`recalc_dirty` 每次都走
   `if deps.requires_full_recalc() || has_spills { recalc_all(); return 总公式数 }`，
   所以「5 步增量 vs 克隆全量」实际是**全量 vs 全量**，范围外的错误缓存从没被验到。
3. 「清障碍」那步往 B9 写 9，本来就没障碍，等于没清。
4. `snapshot` 只收 `formula.is_some()` 的格，溢出子格不在比较范围。
5. `=SUM(A1 A2)` 生成了 `#NULL!` 却从没断言类型，文档里还留了一句
   「若引擎不产生 #NULL! 则等价于 Value 错误」的推测。

六、返工后的设计
----------------
**A. 七种错误 × 真实局部 dirty 路径（簿子里没有任何数组/溢出）**
`error_book()`：数据!A1..A7 = Div0/Na/Num/Name/Value/Ref/Null；
数据!B1 = 0 与 数据!A9 = `=1/B1` 构成真实错误链；汇总!A1=`=数据!A9`、
B1=`=A1&"x"`、C1=`=IFERROR(A1,7)`、D1=`=SUM(A1,2)`。

- `seven_errors_are_typed_after_a_full_recalc`：七种类型逐个断言（含 `Error(Null)`）。
  另用临时探针核对过 `=#NULL!`、`=SUM(A1 A2)`、`=A1 A2` 三种写法都返回 `Error(Null)`，探针已删。
- `a_local_recalc_matches_a_full_recalc_over_the_whole_book`：改 数据!B1（4→8→0）三轮，
  每轮 `recalc_dirty` 返回的脏集合**精确等于 5 格**（数据!A9 + 汇总!A1..D1），
  再与克隆 `recalc_all` 的**整本非空格**逐格比类型与值。
- `a_local_recalc_does_not_touch_an_unrelated_cached_cell`：故意把 汇总!Z31=`=1+1` 的缓存写成 999；
  局部重算后它必须还是 999。若代码走全量回退，它会被改回 2 → 用例失败。
- `fixing_the_error_source_clears_dependents_incrementally`：B1 0→4，A9 由 `#DIV/0!` 变 0.25，
  跨表链变 0.25 / "0.25x" / 2.25。

变异：把 `if deps.requires_full_recalc() || has_spills` 改成 `if true || …`：

    test requirement_three_stage_case_stays_div0 ... FAILED
    test fixing_the_error_source_clears_dependents_incrementally ... FAILED  「走了全量回退」
    test a_local_recalc_matches_a_full_recalc_over_the_whole_book ... FAILED
      第 0 步走了全量回退（算了 12/12 格），不是局部路径
    test a_local_recalc_does_not_touch_an_unrelated_cached_cell ... FAILED
    → 4 failed / 6 passed

**B. SPILL 单独测（如实标注它会整本回退）**
`a_blocked_spill_reports_spill_and_recovers_after_the_blocker_is_removed`：
A9=`=SEQUENCE(2,1)`、**A10** 被 7 占住 → A9 断言 `Error(Spill)`、A10 仍是 7；
删掉 A10 → `recalc_dirty` 返回的总公式数（证明走了全量回退）→ A9=1、A10=2（子格断言），
再与克隆全量逐格比较。

**C. 需求原样场景**
`requirement_three_stage_case_stays_div0`：A1=`=1/0`、B1=1、C1=`=SUM(A1,B1)`；
全算 → 改 B1=2 局部增量（断言只算 1 格）→ 再全算，C1 始终 `#DIV/0!`。

八、对 C01.2 证据的更正
-----------------------
`c01-2-error-persistence.txt` 里的 `book()` 全部是 `formula: None`，只证明了 BOOLERR
（静态错误/布尔）往返，**没有**覆盖 FORMULA 缓存；该文写法容易让人以为公式缓存也验过。
公式缓存以本文件第四节为准，C01.2 的验收范围相应收窄为「静态 BOOLERR + 剪贴板映射 + 外链缓存」。
